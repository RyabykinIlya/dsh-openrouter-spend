## MAJOR — code correctness / user-visible wrong behaviour

### M1. Escalation toast always says "lifetime" for periodic caps

- **Area:** client
- **Location:** `client.js:870-874` (Toast period selection), `client.js:454-495` (`limitState`, the `shared` object)
- **Problem:** the Toast reads `state.limitReset` to choose between `periodToday` / `periodWeek` /
  `periodMonth` / `limitToastPeriodLifetime`, but `limitState` never returns `limitReset`. Verified
  by probe: `Object.keys(limitState({limit: 12, limitRemaining: 1.8, limitReset: 'daily', …}))` =
  `level, limitUsd, remainingUsd, percent, lifetime, resetAtMs, untilResetMs, resetText, runwayMs,
  runwayText, requests, consumed, imminent` — no `limitReset`. The ternary therefore always falls
  through to `t('limitToastPeriodLifetime')`, so a daily-cap toast reads
  *"Key "x" is at 85% of lifetime's $12 limit …"*.
- **Fix:** add `limitReset` to the `shared` object inside `limitState` (or pass it through from the
  caller).
- **Acceptance:** a toast for a `limitReset: 'daily'` key names the day/period, not "lifetime";
  `limitReset` appears in the `limitState` result; a test pins the toast period selection for
  `daily` / `weekly` / `monthly` / `null`.

### M2. Seen-limit never re-arms per period — future warn toasts permanently suppressed

- **Area:** client
- **Location:** `client.js:279-281` (`writeSeenLimit`), `client.js:1307` (the seen check),
  `client.js:1050-1054` (Pill writes on popover open), `client.js:1314-1327` (ToastOverlay
  dismiss/open); design contract at `docs/design/limit-notice.md:287-294`
- **Problem:** the design doc pins the stored key as `` `${keyId}:${level}:${periodStart}` `` with
  the explicit consequence *"The next period re-arms it: a daily cap exhausted yesterday warns again
  today"*. The implementation writes only `` `${keyId}:${level}` ``. Chain: user opens the popover
  (or dismisses a toast) at warn → `seenLimit = 'key:warn'` → next daily period the level goes
  `none → warn` after the refill → `escalates('none','warn')` is true but the seen check matches →
  the toast is suppressed for every future period of that key until it reaches critical.
- **Fix:** include `periodStart` in the stored key (UTC day / ISO week / ISO month / `ever` for
  lifetime caps), exactly as the design doc specifies.
- **Acceptance:** with `seenLimit = 'key:warn:<yesterday>'`, a warn escalation today fires; a test
  covers the re-arm across a period boundary.

### M3. Chip dot stays blue after a failed refresh when good data exists

- **Area:** client
- **Location:** `client.js:936`
- **Problem:** `const dotStatus = data?.status ?? (failure === null ? undefined : 'stale');` — the
  `'stale'` fallback applies only when `data` is null. After the first successful read
  (`data.status === 'ok'`), a later failed fetch keeps `failure !== null` but resolves the dot to
  `'ok'` (blue). ADR-0005 defines the amber dot as exactly *"the last good figures are still on
  screen, but the latest read failed"* — this case. The tooltip/panel/aria do carry the failure, but
  the dot is the at-a-glance signal.
- **Fix:** prefer `'stale'` whenever `failure !== null` and the status is not `error` /
  `no-credential`, e.g.
  `const dotStatus = failure === null ? data?.status : (data?.status === 'ok' ? 'stale' : data?.status);`
- **Acceptance:** with prior good data and a failing fetch the dot is amber (`stale`), not blue; a
  test renders this combination and asserts the dot state.

### M4. `POST /credential` does not invalidate an in-flight refresh

- **Area:** server
- **Location:** `index.js:1051-1056` (the handler's cache reset + `await current()`),
  `index.js:966-990` (`current()`; line 972 returns the existing `inFlight`, line 978 repopulates
  the cache on completion)
- **Problem:** the handler sets `cached = undefined; failures = 0; lastAttemptMs = 0` and then
  `await current()`. When a read is already in flight, `current()` returns that same promise; its
  completion then unconditionally writes `cached = { expiresAt, payload }`, defeating the
  invalidation. The POST responds with the pre-write result and the cache pins it for a full
  `refreshSeconds`. **Reproduced:** with `credStore` switched from `old-key` to `new-key` while a
  gated read was in flight, `POST /credential` answered `200` with `todaySpend: 1` (the old key's
  figures; the new key's would be `9`), the upstream call was made with `Bearer old-key`, and two
  later polls were served from the poisoned cache without any new fetch.
- **Fix:** add a generation counter bumped on credential writes; in `current()`'s completion,
  discard (or immediately re-read) when the generation is stale — or on POST, if `inFlight` exists,
  await it and then force one fresh read before answering.
- **Acceptance:** saving a key while a read is in flight answers with figures read under the **new**
  key (or an explicit fresh read), and the cache does not hold the pre-write payload.

### M5. Bare `GET /keys`: default exclusions, pagination and workspace scoping unhandled

- **Area:** server
- **Location:** `index.js:513-514` (`queryKeys`), `index.js:505` (the `disabled` field),
  `index.js:490-509` (`readKeyLimits`)
- **Problem:** the request is `${apiBase}/keys` with no query parameters. Per the published
  OpenRouter API ([List API keys](https://openrouter.ai/docs/api/api-reference/api-keys/list-api-keys),
  [APIKeys SDK reference](https://openrouter.ai/docs/client-sdks/python/sdks/apikeys/README)):
  `include_disabled` defaults to `false`, expired keys are excluded by default
  (`include_expired`), `offset` paginates, and only the default workspace's keys are returned.
  Consequences: (a) the payload's `disabled` field can never be `true` and is in fact unread by the
  client — dead weight; (b) a limited key that is disabled, expired, in another workspace, or past
  the page boundary silently vanishes from `limits`, and the client shows "limit unknown" for a key
  that has a cap — silent misreporting of exactly the class ADR-0002 says to avoid.
- **Fix:** request `?include_disabled=true`; decide explicitly on `include_expired`; loop `offset`
  until a short page (or verify and document that the response is unpaginated); document the
  default-workspace limitation or iterate workspaces; drop the `disabled` field (and its test) if it
  stays unreachable.
- **Acceptance:** a disabled key with a limit appears in `limits` (or the limitation is documented);
  pagination is handled or proven unnecessary; `disabled` is either reachable or removed.

### M6. No test pins `collect()`'s auxiliary-failure containment

- **Area:** tests
- **Location:** `index.js:766-775` (the `limitsError` / `burnError` catch blocks; the `sessionsError`
  and `lineageError` paths are analogous)
- **Problem:** mutation-verified: removing the `.catch` that turns a failed `/keys` read into
  `limitsError` leaves the suite at 88/88 green. A regression would take the whole chip down
  (summary goes `stale`) when an auxiliary read fails — the exact containment the code comments and
  ADR-0003 promise. The scratch E2E harness catches this mutation (3 assertions fail).
- **Fix:** add a test that stubs `globalThis.fetch` so `/keys` (or the hourly burn) fails while the
  analytics queries succeed, drives `apply()`'s handler (or `collect()` through the same seam), and
  asserts the payload still carries figures plus `limitsError` / `burnError` and `status: 'ok'`.
- **Acceptance:** deleting the `.catch` blocks turns the new test red; restoring them turns it green.

## MAJOR — release process (cheap fixes, blockers for publishing)

### M7. `postinstall: "lefthook install || true"` runs for every consumer

- **Area:** release
- **Location:** `package.json:51` (script), `package.json:57` (`lefthook` devDependency)
- **Problem:** `lefthook` is a devDependency and npm never installs devDependencies of a
  dependency, so every consumer's install prints `sh: lefthook: command not found` on stderr,
  masked to exit 0 by `|| true`. The `|| true` also masks genuine hook-install failures for
  contributors, and a `postinstall` in a published dependency is exactly what security-conscious
  users and pnpm 10's default script blocking object to.
- **Fix:** use `prepare` (runs for clones/contributors, not for registry consumers), or drop the
  script and document `npx lefthook install` in `CONTRIBUTING.md`.
- **Acceptance:** installing the packed tarball in an empty directory produces no stderr noise and
  no lifecycle surprises; contributor hooks still install per the docs.

## MINOR

### Server

- **m1. One shared timeout for the whole refresh; config says "per-request".**
  `index.js:938` creates a single `AbortSignal.timeout(config.timeoutMs)` threaded into 7 upstream
  operations (analytics, credits, sessions ×2, keys, hourly burn, lineage listing), while
  `index.js:123-124` describes "Per-request deadline". Auxiliary slowness can flip the whole
  summary to `stale`. **Fix:** per-query timeouts, or reword the description and consider a higher
  default.
- **m2. 429 handling ignores the server's retry hints.** `index.js:156` classifies 429 as
  `rate-limit` but the ladder is fixed (15/30/`refreshSeconds`); `Retry-After` /
  `X-RateLimit-Reset` headers are not read. **Fix:** parse the hints and take
  `max(ladder, server hint)`.
- **m3. `warnConsumedFraction` / `criticalConsumedFraction` not cross-validated.**
  `index.js:125-128` permits warn ≥ critical (e.g. 0.9/0.5), making the warn tier unreachable and
  the escalation jump straight to critical. **Fix:** validate `warn < critical` at activation or
  clamp the effective warn.
- **m4. Duplicate key names silently overwrite.** `index.js:501` is last-wins; two limited keys
  sharing a name misjoin analytics spend to an arbitrary one with no signal (ADR-0002 names
  duplication as the join's known risk). **Fix:** detect duplicates among limited keys, drop both
  and surface a note (the client's `limitUnknown` path can carry it).
- **m5. Lineage read lists and clones the whole session corpus every refresh.**
  `index.js:379` calls `ctx.sessionQuery.listSessions(signal)`, O(all sessions ever), inside the
  shared timeout, every refresh. **Fix:** cache keyed by a corpus version if available, filter or
  paginate, at least measure.
- **m6. POST route's final `await current()` is outside any try/catch.** `index.js:1056` — if
  `current()` rejects (only when `ctx.credentials.resolve/describe` throw) the rejection escapes and
  the host answers a bare 400, inconsistent with the GET route's JSON 502 (`index.js:1008-1016`).
  **Fix:** wrap and mirror the GET route's error reply.
- **m7. `burnWindowDays` max invites configurations that can never succeed.** `index.js:50` +
  `index.js:129` + the refusal at `index.js:591-592`: 30 days × 24 h × ≥7 fully-active keys exceeds
  `MAX_BURN_ROWS = 5000` on every refresh. Refuse-not-truncate is right, but the schema allows the
  trap. **Fix:** document the interaction or lower the max (e.g. 14).

### Client

- **m8. `failureLabelKey` has no `'request'` case though both halves emit it.**
  `client.js:708-719` (switch) vs `client.js:770` (`code: response.status === 502 ? 'host' :
  'request'`) and `index.js:141-169` (`describeFailure` returns `request` for 4xx). A classified 4xx
  renders "the reason is unknown" while the raw detail below tells the truth. **Fix:** add
  `case 'request': return 'errorRequest';` with the key in all three dictionaries (or map non-502
  HTTP failures to `host`/`server`).
- **m9. Toast copy does not distinguish warn from critical.** `limitToastWarn` / `limitToastCritical`
  (and the NoEstimate pair) are byte-identical in all three locales (`client.js:1593-1596`,
  `1668-1671`, `1751-1754`) and the Toast renders no level marker. **Fix:** differentiate the copy
  or collapse to one key pair.
- **m10. `levelRef` is not reset when the tracked key changes.** `client.js:922`, `1042-1045`,
  `1259`, `1301-1310` — switching from a critical key to a warn key keeps the old hysteresis and
  escalation history, which can swallow the new key's toast. **Fix:** reset `levelRef.current` to
  `'none'` (and consider clearing `toastLevel`) on `keyId` change.
- **m11. Retry button label is stale during a background poll.** `client.js:817-818` sets
  `refreshing` only for forced reads, while `client.js:1245` disables the button during any poll —
  so it reads "Retry now" while disabled. **Fix:** derive the label from the same state that
  disables it.
- **m12. `windowedBurn` parses zone-less `date__hour` strings in local time.**
  `client.js:306`, `318-321`, `341` — `Date.parse` on `YYYY-MM-DDTHH:00:00` (no designator) skews
  the 7-day window by the reader's UTC offset (up to ±14 h; immaterial for a week but real).
  Related inconsistency: `windowedBurn` keeps numeric-ts buckets while `closedDayTotals` skips them
  (~`client.js:398`) — unreachable with the current host. **Fix:** parse as UTC (append `Z` or use
  `Date.UTC`), make the sibling handling consistent.
- **m13. The 1 s coalescing window only merges near-simultaneous calls.** Pill (user interval) and
  ToastOverlay (host cadence) on misaligned schedules still issue separate requests per period.
  Scoped by design per the code comment; noting it because the commit message promised "two HTTP
  requests per tick" would become one.
